Investigated 2026-07-16: the Intel runtime "didn't work on Windows with no errors". Package was fine; three real causes:

1. **Host bug:** plain `LoadLibraryA` can't resolve the DLL's co-located dependencies (no RPATH on Windows). The loading host must use `LoadLibraryExA` + `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR` (needs an absolute path) and log `GetLastError`/`dlerror`.
2. **Runtime bug:** `initialize_logger` called `exit(1)` when `runtime.log` (CWD-relative; unwritable for Windows services) couldn't be created — killing the host. Fixed in `runtime-library/src/runtime_utils.cpp`: console-only fallback + warning. Verified with unwritable log_file → init SUCCESS.
3. Silent-failure ergonomics: failures now log root cause instead of generic "Runtime not initialized."

Also renamed `runtime_get_name()` → "OAAX Intel" (`runtime_core.cpp`, asserted in `tests/runtime/simple_test.cpp`).

Diagnostic tool: `tests/runtime/windows_load_test.c` (PE bitness check, per-dep probes, plugin-DLL presence, CWD writability, `--init`). Must be built from the **x64** Native Tools prompt.

The same audit applies to the other vendor runtimes in the OAAX organization.

**2026-07-17 — DLL-pinning / unloadability fix** (FreeLibrary not releasing the DLL):
- spdlog async pool was a `static` in `initialize_logger` — its worker thread (code inside our lib) survived `runtime_cleanup`, pinning the DLL on Windows and risking a loader-lock deadlock at unload. Fixed: pool owned in a global `shared_ptr`, joined via `shutdown_logging()` called at the end of `runtime_cleanup` (after `destroy_logger`).
- Linux unloadability required three build changes in `runtime-library/CMakeLists.txt`: `-fno-gnu-unique` (GNU-unique symbols make glibc refuse to unload), `-fvisibility=hidden -fvisibility-inlines-hidden`, and a linker version script `cmake/runtime.map` exporting only the 9 OAAX symbols (otherwise NODELETE libs like libstdc++/libopenvino bind our vague-linkage/RTTI copies — "relocation dependency" — pinning us forever).
- Genuine unload exposed a latent crash: init + dlclose WITHOUT runtime_cleanup segfaults (destructors/unmap under live threads; previously masked because dlclose was a NODELETE no-op). Fixed with a per-DSO `atexit(runtime_cleanup)` hook registered inside `runtime_init` — Linux only; on Windows joining threads in DLL_PROCESS_DETACH deadlocks (loader lock), hosts must call cleanup before FreeLibrary.
- Verified: proper cycle now truly unmaps on dlclose; no-cleanup paths don't crash; simple_test suite passes. Only surviving thread after cleanup is an Intel OpenCL driver thread (libigdrcl — driver-owned, not our code).
- Gotcha discovered while testing: `printf("%d %d", init(cfg), cleanup())` evaluates args right-to-left in GCC — cleanup ran BEFORE init in an early test, faking a "still pinned" result. Watch for this in repro programs.

**2026-08-05 — the `ov::shutdown()` call added above was itself a regression.** `ov::shutdown()` deletes all of OpenVINO's static-duration state and is documented as final-teardown-before-unload only — not safe to call from a `runtime_cleanup()` that a subsequent `runtime_init()` can follow *in the same loaded module*. But that repeated init/cleanup cycle is exactly what a pipeline/model reselect does on the host side (no DLL reload involved), and it's a contract the OAAX API is required to support (the OAAX reference implementation's `lifecycle_test.cpp` explicitly tests repeated cycles — this repo had no equivalent test, which is why the regression wasn't caught). Calling `ov::shutdown()` there raced the next `runtime_init()`'s fresh `ov::Core()` against TBB's own internal NUMA/topology-binding teardown, corrupting memory inside `tbbbind_2_5.dll` — but **only on multi-NUMA-node hardware**, which is why "double init/cleanup OK" verification on a single-NUMA dev box missed it. Fixed by removing the `ov::shutdown()` call (PR #23, merged to `oaax-v2` at `a361dd42`); added `tests/runtime/lifecycle_test.cpp` covering full init/load/cleanup cycles plus an inference round-trip across a teardown/reinit, so this class of bug can't silently return. Note: the TBB dependency DLLs (`tbb12.dll`, `tbbbind_2_5.dll`, `tbbmalloc.dll`) were also observed still locked *even with* `ov::shutdown()` in place — so removing it doesn't sacrifice a guarantee that was actually working for the Windows hot-swap/unload case it was added for.

**2026-09-01 — why TBB DLLs specifically never release (found the actual mechanism).** `ov::shutdown()` was a red herring for this symptom — its own docs only cover OpenVINO's *own* static-duration state (frontends, plugin registry), not TBB's. TBB ships as separate DLLs (`tbb12.dll`, `tbbbind_2_5.dll`, `tbbmalloc.dll`) with their own process-global thread pool (the "market"), lazily started and kept alive indefinitely for worker-thread reuse across `ov::Core` instances — oneTBB's documented lifetime model requires an explicit `tbb::finalize(task_scheduler_handle)` (blocks until every worker thread exits) to tear it down; nothing about destroying an `ov::Core` does this automatically. On Windows, a DLL with live threads whose start address is inside it typically self-pins (`GetModuleHandleEx(..., GET_MODULE_HANDLE_EX_FLAG_PIN)`) so it can never be unmapped while those threads run — so once any inference happens, `tbb12.dll` et al. are locked for the life of the host process, regardless of `runtime_cleanup()`/`FreeLibrary()` cycles on our own DLL.

OpenVINO has a knob for this: `ov::force_tbb_terminate` (an `ov::Core` property, present since 2022.1, added specifically for "unload TBB upon OpenVINO library unloading") — explicitly terminates TBB's market when the `Core` that had it set is destroyed. We've never set it. **Untested risk**: this does the same underlying TBB-market teardown that raced `tbbbind_2_5.dll` in the regression above, so it needs the same multi-NUMA-node repro machine before it goes anywhere near `runtime_cleanup()` — do not add it without that test, and prefer scoping it to a final teardown path (last cleanup before the DLL itself is expected to unload) rather than every init/cleanup cycle.

Practical takeaway for hosts: don't design a runtime-reselect/update flow around being able to delete/overwrite the old runtime's DLLs while the host process is still running with it loaded — on Windows this is close to structurally impossible with OpenVINO+TBB as-is. A staged-extraction-then-swap-on-restart approach sidesteps the problem without touching TBB lifecycle at all.
